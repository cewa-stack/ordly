ORDLY · plan rozbudowy · 31 lipca 2026 · v2

Dwie aplikacje, jeden backend: telefon do podglądu, laptop do zarządzania

Przeczytałem 7 plików z files/ i zestawiłem je z rzeczywistym stanem repo ORDLY. Po Twojej korekcie: telefon pokazuje magazyn, zamówienia, zwroty, dyskusje i skrzynkę mailową — wyłącznie do podglądu, z pushem. Laptop (nowa aplikacja Electron) dostaje to samo z akcjami, plus hurtownię, OLX i statystyki, których na telefonie świadomie nie ma. Zero kodu napisanego dzisiaj — to materiał do Twojej akceptacji.

Pliki źródłowe: appplans_00…06.md Repo sprawdzone: src/ (backend) + mobile/ (PWA) Kod dzisiaj: żaden

Najpierw korekta założeń

Pliki planistyczne opisują architekturę, której w Twoim repo nie ma. Zanim cokolwiek zaplanuję dalej, to trzeba nazwać wprost — inaczej cała kolejność wdrażania z appplans_00 prowadzi w złą stronę.

Nazewnictwo z planu → rzeczywistość

Plan zakłada: backend RPi nazwany "Comcio", desktop nazwany "Cewastack".

W repo jest: jeden backend FastAPI na Raspberry Pi pod nazwą ORDLY (usługa ordly.service) + bot Telegram + aplikacja RN/Expo (PWA). Osobnej appki desktopowej faktycznie nigdy nie było — budujemy ją teraz od zera jako Electron, pod nazwą ORDLY, nie jako drugi produkt z inną marką.

Architektura pluginów jest węższa niż plan zakłada

Plan (appplans_02/05) zakłada listę registered_plugins odpytywaną równolegle (Allegro + OLX naraz). W rzeczywistości Container.build_plugin() wybiera jeden aktywny plugin na podstawie MARKETPLACE_PROVIDER — Amazon i eBay istnieją tylko jako puste foldery-szkielety, nigdy nie działały równolegle z Allegro.

Żeby OLX działał obok Allegro (a nie zamiast), trzeba najpierw rozszerzyć scheduler o wielu jednoczesnych dostawców — to realna, wcześniej niezaplanowana zmiana architektoniczna, nie tylko "dodaj plugin".

Fundament z modułu 02 już częściowo istnieje

Sync silnik, Event Bus, scheduler cykliczny i Web Push — to wszystko już działa (core/event_bus/, scheduler/jobs/sync_orders_job.py, infrastructure/webpush/). Zwroty (customer_returns) są już synchronizowane i emitują zdarzenie OrderReturnCreated — tylko nigdzie w UI nie są jeszcze pokazane. Nie trzeba tego budować od zera, tylko rozszerzyć.

Twoja korekta — podział ról między aplikacjami (potwierdzone, v2)

Telefon (PWA, tak jak dziś): podgląd + powiadomienia push, zero akcji. Konkretnie cztery obszary: Magazyn (stan), Zamówienia, Zwroty i anulowane, Dyskusje i Skrzynka (maile Allegro/OLX) — wszystko tylko do odczytu, z pushem przy nowym zdarzeniu. Kliknięcie w powiadomienie o dyskusji czy mailu otwiera podgląd, nie pole odpowiedzi — z komunikatem „Odpowiedz na laptopie". Poza tym tylko techniczne minimum: logowanie, Face ID, wylogowanie, test powiadomień.

Laptop (nowa aplikacja Electron): pełna wersja ORDLY do zarządzania — te same cztery obszary co na telefonie, ale z akcjami (odpowiedź na dyskusję, itd.), plus to, czego na telefonie świadomie nie ma: Hurtownia (wysyłka maila) i OLX, oraz przeniesione tam Statystyki.

Backend pozostaje jeden (RPi, ordly.service) — obie aplikacje to tylko klienci tego samego API, zgodnie z zasadą "Pi = jedyne źródło prawdy" z oryginalnego planu. Ten sam endpoint GET /returns czy GET /disputes karmi obie appki — różnica jest tylko w tym, czy UI pokazuje przycisk akcji.

Stan faktyczny — punkt wyjścia

Warstwa
Co realnie działa dziś
Backend
FastAPI + aiogram + APScheduler + SQLite/WAL, Clean Architecture (domain / services / infrastructure / repositories), Alembic już skonfigurowany.
Sync
sync_orders_job co SYNC_ORDERS_INTERVAL_SECONDS — zamówienia, anulowania, zwroty. Event Bus emituje OrderCreated/Updated/Cancelled/ReturnCreated.
Powiadomienia
Web Push (VAPID) już wysyła do PWA + bot Telegram do admina. Brak Expo/FCM — i nie jest potrzebny, PWA nie tego wymaga.
Klient (dziś)
Jedna appka RN/Expo (PWA): Home, Orders, OrderDetail, Stock, StockItem, Stats, Settings, Login + Face ID. Po zmianie: Stats wędruje na desktop, reszta zostaje jako czysty podgląd.
Klient (do zbudowania)
Aplikacja Electron na laptopa — nie istnieje jeszcze ani jedna linijka. Nowy szkielet: React + TS + Vite (spójnie z resztą stacku), logowanie przez ten sam POST /api/v1/auth/login co mobile.
Marketplace
Allegro w pełni wdrożony (auth, client, mapper). Amazon/eBay — puste szkielety. OLX — brak w ogóle.
Sekrety
Wszystko w .env na Pi: Allegro, Telegram, VAPID. Brak SMTP, brak IMAP, brak OLX.

Kolejność wdrażania

Osiem etapów. Etap 0 to fundament, bez którego nic dalej nie ma gdzie żyć — dopiero potem dokładam moduły. Telefon dostaje tylko jeden etap na końcu: przycięcie do czystego podglądu.

00Szkielet aplikacji Electron na laptopa
nowa aplikacja

Musi powstać jako pierwsze — wszystkie kolejne etapy to ekrany wewnątrz tej appki. Bez tego nie ma gdzie umieścić zwrotów, dyskusji, hurtowni ani skrzynki.

Reużywam
  • POST /api/v1/auth/login, ORDLY_API_TOKEN, adres Tailscale
Buduję nowe
  • Electron + React + TS + Vite, okno + nawigacja boczna
  • Ekran logowania (reużywa istniejący endpoint), token w electron-store zaszyfrowany
  • Zakładka Magazyn — z edycją: POST /stock/{sku}/adjust, linkowanie ofert, nowe produkty (te endpointy już istnieją)
  • Zakładka Zamówienia — podgląd + ręczny POST /orders/sync i wyszukiwanie; bez edycji statusu — backend go nie udostępnia, status idzie wyłącznie z Allegro, więc taki przycisk nie powstanie
desktop/ (nowy katalog) · desktop/electron/auth.js · desktop/src/App.tsx
01Zwroty i anulowane
głównie reuse backendu

Dane już płyną do bazy i emitują zdarzenia (customer_returns, OrderReturnCreated) — brakuje tylko endpointu i ekranów. Jeden endpoint karmi od razu obie appki: desktop dostaje zakładkę pełną, telefon — podgląd + push.

Reużywam
  • Event bus, dane już zsynchronizowane, web push
Buduję nowe
  • Endpoint GET /api/v1/returns + event push przy nowym zwrocie
  • Zakładka „Zwroty i anulowane" w Electronie (desktop)
  • Ekran „Zwroty" w PWA — lista read-only + push, bez akcji (mobile)
api/endpoints/returns.py · desktop/src/features/returns/ · mobile/src/screens/ReturnsScreen.tsx
02Dyskusje Allegro
nowa funkcja

Zero istniejącego wsparcia — model, sync i odpowiadanie powstają od zera. Wymaga weryfikacji aktualnej nazwy scope'u/endpointu w dokumentacji Allegro przed kodowaniem (nazwy bywają zmieniane).

Reużywam
  • Wzorzec pluginu Allegro (mapper/client), scheduler, event bus
Buduję nowe
  • DisputeModel + migracja Alembic
  • POST /disputes/{id}/reply (proxy do Allegro, token zostaje na Pi)

03Mail do hurtowni
nowa funkcja

Niezależny od reszty. Wysyłka SMTP dzieje się w backendzie na Pi (jedyne miejsce z sekretami) — Electron woła endpoint, nie trzyma hasła SMTP lokalnie, zgodnie z zasadą "zero sekretów w kliencie".

Reużywam
  • Wzorzec .env + serwis w warstwie services/
Buduję nowe
  • WholesalerModel, wholesaler_service.py (SMTP)
  • SMTP_HOST/PORT/USER/PASS w .env na Pi
  • Przycisk „Zamów u hurtowni" w Electronie + modal edycji treści
services/wholesaler_service.py · desktop/src/features/wholesalers/
04Skrzynka — maile Allegro/OLX (Gmail)
nowa funkcja

Potwierdzone: Gmail. Wymaga hasła aplikacji (app password) w koncie Google — 2FA musi być włączone. IMAP odpytywany rzadziej niż sync zamówień (co 5 min, nie 60s), żeby Gmail nie throttlował.

Reużywam
  • Scheduler (drugi, wolniejszy job), event bus, wzorzec service/model
Buduję nowe
  • mail_watcher.py (IMAP przez aioimaplib)
  • MailMessageModel + endpointy odczytu + push przy nowym mailu
  • Zakładka „Skrzynka" (lista + podgląd, split-view) w Electronie (desktop)
  • Ekran „Skrzynka" w PWA — ta sama lista i podgląd, tylko bez akcji wysyłki (mobile)
services/mail_watcher.py · desktop/src/features/mailbox/ · mobile/src/screens/MailboxScreen.tsx
